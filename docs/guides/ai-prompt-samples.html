Harunobu が LLM に送っているもの

ルールエンジン Harunobu は、決定論的なルールで判断しきれない箇所だけを LLM に問い合わせます。このページは、その問い合わせを実際に送信された HTTP リクエストのまま集めたものです。読み取ったコードから書き起こしたものではありません。

取得方法: Docker コンテナ内に OpenAI 互換のモックサーバを立て、HARUNOBU_AI_PROVIDER=openai と HARUNOBU_AI_API_BASE をそこに向けて、tests/sample_by_mr_rules/samples/ の xlsx / csv 35 ファイルを Analyzer(mode="thorough") で解析しました（うち 1 ファイルは拡張子偽装の検出で読み込み段階で拒否）。ルールから呼ばれなかったメソッドは、サンプルの実データを入れて直接呼び出しています。対象コード: main 23665d8。

まず結論

  • 表全体は送っていません。送るのはヘッダー文字列、1 列分の値（最大 50 件）、ユニーク値一覧、問題のありそうなセル値だけです。行全体を送るのは L3-09 の先頭 3 行だけです。
  • 表データは CSV や JSON ではなく、日本語の文の中に埋め込んだテキストです。たとえば [0] ヘッダー: 「数値1」, サンプル値: 12.4, 18.9, 25, 9.6、行3: '北海道'、'北海道', '青森県'、a | b | c など、メソッドごとに書式が違います。
  • プロンプトはすべて日本語です。system メッセージは使わず、user メッセージ 1 通に指示・データ・JSON の回答例をまとめています。半数以上のメソッドは先頭に共通の「行政データのエキスパートです」という前置き（このページでは薄い色で表示）が付きます。
  • 送信パラメータは全件同じで、temperature: 0.1 と response_format: {"type": "json_object"} です。ただし、多くのプロンプトは配列（[...]）での回答を求めています。json_object モードはトップレベルがオブジェクトであることを前提にするプロバイダが多いので、本物のモデルでは衝突する可能性があります（モックでは検証できないため推定）。
  • 今回の thorough 解析で実際に送られたのは 224 リクエストで、すべてテキストのみでした。画像を使う L1-05 / L1-11 は 185 回呼ばれましたが、すべて送信前に TypeError で失敗し、例外は握りつぶされていました（詳細は analyze_sheet_visual）。

いつ LLM が使われるか

モードごとに評価するレベルが決まり（harunobu/core/models.py:486-490 の _MODE_LEVELS）、そのレベルのルールのうち AI を使うものだけが LLM を呼びます。AI 呼び出しは常に決定論チェックの補完で、条件に合う列やセルが無ければ呼ばれません。ルールはスレッドプール（最大 8 並列）で動くので、1 シートの中で複数の問い合わせが同時に飛びます（harunobu/core/analyzer.py:213-216）。
